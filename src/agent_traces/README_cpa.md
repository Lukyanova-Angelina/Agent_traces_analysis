# CPA-разметка трейсов агентов (SberAgentTaskArena)

Статус: **пилот**. Пайплайн работает от БД до кодбука, но результаты пока не годятся как измерение.

## 1. Суть статьи

Статья: *Canonical Procedural Actions: An Auditable Annotation Protocol for Tool-Use Agent Traces* (arXiv:2609.24264).

**Что предлагается.** Протокол аннотации трейсов агентов. Единица разметки — *CPA*: наблюдаемая процедурная функция, которая описывается четырьмя полями: цель (proximal goal), выход (principal output), изменение состояния (state change), предусловия (preconditions). Каждая CPA привязана к *якорю*, то есть первому событию агента, которое её реализует, и ссылается на контекст (ответ клиента, результат инструмента) отдельно. Одно сообщение может давать несколько CPA, порядок между ними не выводится.

**Как строится словарь.** Открытая индукция на выборке → консолидация с записью решений (merge/split/reject) → применение на новых трейсах → заморозка → применение к остальным данным. Отложенная выборка не открывается при построении.

**Главные результаты (τ3-Retail, 24 функции).**
- Согласие двух изолированных LLM-прогонов на 32 траекториях: A = 0.982. Это согласие, а не точность: эталона людей нет.
- Согласие по ссылкам на контекст заметно ниже: 0.798.
- Простое эндпоинт-правило воспроизводит разметку инструментов с A = 0.997. Значит, LLM-разметка нужна в основном для сообщений ассистента, где и происходят почти все расхождения (A = 0.971).
- Ограничения, которые авторы сами признают: клиппинг аргументов до 110 символов, нефиксированная температура, данные с пересекающимися задачами, отсутствие человеческой проверки.

**Что статья не доказывает.** Что CPA точнее, что помогает диагностике ошибок, что словарь переносится на другие домены. Перенос на другой домен требует нового словаря.

## 2. Суть кода

Один файл, подкоманды:

| Команда | Что делает | Результат |
|---|---|---|
| `extract` | Читает `v_agent_trace_actions` из PostgreSQL, группирует подряд идущие вызовы с одинаковыми (инструмент, объект, шаг) в эпизоды | `episodes.csv` |
| `sample` | Стратифицированная выборка: топ-пары, средние, хвост, длинные эпизоды, эпизоды с ошибками | `sample.csv`, `pilot.csv` |
| `label` | LLM предлагает метку и четыре поля, либо воздерживается; запись в JSONL, докачка без повторов | `proposals.jsonl` |
| `consolidate` | LLM кластеризует метки в канонические функции; непокрытые метки назначаются или становятся одиночными | `codebook.json`, `labelled.csv` |
| `report` | Частоты меток, метки с именем инструмента внутри, причины воздержаний | вывод в консоль |
| `agreement` | Согласие двух прогонов по формуле A из статьи | вывод в консоль |

Конфиг через `.env`: `ATA_DB_URL`, `CPA_API_KEY`, `CPA_API_BASE`, `CPA_MODEL`, `CPA_TEMPERATURE`.

**Порядок запуска:** extract → sample → label (сначала pilot) → report → consolidate → agreement (на двух прогонах).

## 3. Что нужно поправить

Приоритет сверху вниз. Первые четыре блокируют любые выводы.

1. **Дубли потоков.** Один вызов может быть в нескольких потоках трейса (native, tool_trace, bridge). Фильтровать по `stream_kind = 'native'`. Проверить значения: `SELECT stream_kind, count(*) FROM v_trace_index GROUP BY 1;`
2. **Качество попыток.** Брать только `chain_attempts.valid_for_scoring IS TRUE`. Отсеянные логировать.
3. **Имена инструментов по средам.** Сделать таблицу соответствий «имя → семейство» для opencode, hermes, openclaw, ouroboros и direct_mcp (`excel_*`, `office_*`, `filesystem_*`). Имена выгрузить из данных.
4. **Парный дизайн.** Стратифицировать по `(dataset_task_id, harness)`. Одна задача прогнана в пяти средах, и это готовое парное сравнение.
5. **Аргументы.** Использовать нативные вызовы, а не маркеры bridge (у OpenClaw shell-команды заменяются хешами). Поднять обрезку с 400 символов или брать поля целиком.
6. **Якоря в сообщениях ассистента.** Сейчас размечаются только вызовы инструментов, а там эндпоинт-правило уже покрывает почти всё. Без сообщений ассистента работа описывает половину картины.
7. **Baseline перед LLM.** Построить эндпоинт-правило для xlsx/docx-инструментов и сравнить с LLM на тех же эпизодах. Если разница мала, LLM на вызовах не нужна.
8. **Согласие.** Сейчас `agreement` считает по эпизодам, а не по якорям, как в статье. Температура по умолчанию 0, поэтому два прогона почти наверняка совпадут и цифра будет завышена. Нужна температура выше нуля или другой разметчик.
9. **Заморозка словаря.** Словарь строить на части задач, оценивать на отложенных. Решения по объединению меток записывать в файл, а не делать молча.
10. **Проверить схему.** Колонки `v_agent_trace_actions` (`event_order`, `action_block_index`, `action_status`, `arguments`) не сверены со словарём данных.
## 3. Статус по пунктам
 
### Закрыто
 
- **Эпизоды и выборка** (`cpa.py`): группировка по (инструмент, объект, шаг), стратификация.
- **Открытая индукция** (`label`): абстейны, докачка, сохранение каждой попытки.
- **Консолидация** (`consolidate`): без fuzzy-merge, непокрытые метки помечаются вручную.
- **Согласие** (`agreement`): формула A из статьи, но на уровне эпизода.
- **Словарь инструментов** (`taxonomy.py`): покрывает `excel_*`, `filesystem_*`, `docx_*`, `office_officecli` и нативные имена. Непокрытые уходят в `Other` и печатаются.
- **Детерминированный baseline** (`taxonomy.py`): разметка по инструменту и аргументам, можно сравнивать с LLM.
- **Разметка мыслей** (`taxonomy.py`): rule-based baseline.
### Нужно закрыть
 
- Фильтр `stream_kind = 'native'` в `cpa.py` и `taxonomy.py`. Сейчас один вызов может считаться несколько раз.
- Фильтр `chain_attempts.valid_for_scoring IS TRUE` и исключение `is_canary` (в docstring заявлено, в SQL нет).
- Таблица имён инструментов для opencode, hermes, openclaw, ouroboros, direct_mcp. Непокрытые имена выгрузить из данных.
- Нативные вызовы вместо маркеров bridge для OpenClaw.
- Парная стратификация по `(dataset_task_id, harness)`.
- Якоря в сообщениях ассистента (сейчас только вызовы инструментов).
- Сравнение трёх наборов признаков: сырые имена, `actonomy`, пара `(actonomy, subaction)`. Кода сравнения нет.
- Журнал решений по словарю и заморозка словаря на части задач.
- Сверка колонок `v_agent_trace_actions` (`event_order`, `action_block_index`, `action_status`, `arguments`) со словарём данных.
- В `taxonomy.py`: один из двух словарей CoALA (`ACTONOMY_TO_COALA` и `ACTONOMY_TO_coala`), ранний выход для пустого датафрейма.
- Таблица объёма: число валидных попыток на класс «модель + харнес».
### Критично (блокирует выводы)
 
1. **Дубли потоков.** Завышают `n_actions`, частоты и признаки цепочек.
2. **Невалидные попытки.** Попадают в классы как шум. Нужен `valid_for_scoring IS TRUE`.
3. **Ключи аргументов по моделям.** Код читает только `command`. Для Qwen, Llama и GigaChat ключи могут отличаться (`cmd`, `script`, строка). Тогда команды чтения будут размечены как `Executing`. Проверка:
```sql
SELECT model_identifier, jsonb_object_keys(arguments::jsonb) AS k, count(*)
FROM v_agent_trace_actions GROUP BY 1, 2;
```
4. **Мысли на русском.** Regex-паттерны английские. Если ответы по-русски, почти всё попадёт в `Other`, и это будет ложный результат. Проверка доли кириллицы:
```python
df["text"].str.contains(r"[а-яА-ЯёЁ]").mean()
```
5. **Утечка задач.** Если классификатор обучать и тестировать на цепочках одной задачи, точность завышена (одна задача идёт в пяти средах). Делить по `dataset_task_id`.
### Важно, но не блокирует
 
- Температура 0 в разметке: два прогона совпадут почти всегда, согласие завышено. Нужна температура выше нуля или другой разметчик.
- Клиппинг аргументов в промпте (400 символов). Для XLSX и DOCX может терять диапазоны и значения.
- Правила по командам без границ слов: `"cat "` совпадает с `concat `, `"ls "` с `tools `. Нужны `\b`.
- Решение `message`: `Communication` в legacy, `Grounding/with_users` в новой разметке. Записать в README.
