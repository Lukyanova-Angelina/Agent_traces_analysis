# Классификация цепочек действий LLM-агентов
 
## Цель
 
Определить, по каким признакам поведения агента в цепочке действий можно отличать связки **модель × харнесс**. Объект классификации — цепочка действий (попытка), а не отдельное событие.
 
Данные: трейсы бенчмарка SberAgentTaskArena (задачи обработки XLSX и DOCX). Одна задача прогнана в пяти средах: `opencode`, `hermes`, `openclaw`, `ouroboros`, `direct_mcp`. Модели в основном бесплатные (GigaChat, Qwen, Llama и др.).
 
## Данные
 
PostgreSQL, база `ata_logs_import`. Строка подключения задаётся переменной `ATA_DB_URL` в `.env`, в коде её не хранить.
 
Используемые представления:
- `v_chain_attempts`: попытки цепочек, исход, метаданные (харнесс, модель, `task_score`, `full_pass`).
- `v_agent_trace_actions`: вызовы инструментов (имя, аргументы, статус).
- `v_agent_trace_full`: события с ролями `user`, `assistant`, `tool`.
- `v_trace_index`: потоки трейсов и их тип (`stream_kind`).
Словарь полей: `DATA_DICTIONARY.md`.
 
## Компоненты
 
| Модуль | Что делает | Статус | Подробнее |
|---|---|---|---|
| `taxonomy.py` | Детерминированная разметка действий по Act-ONOMY (`actonomy`, `subaction`) и CoALA (`coala`); rule-based классификация мыслей ассистента | baseline, есть проблемы | — |
| `graphectory_pipeline.py` | Граф по каждой попытке: узлы-действия и результаты, рёбра по времени, объекту и повторам. Около 60 признаков, включая XEPV-группы действий | рабочий черновик | `README_graph.md` |
| `cpa.py` | Семантическая разметка эпизодов по протоколу CPA: открытая индукция LLM, консолидация в кодбук, мера согласия | пилот | `README.md` в папке CPA (старый) |
 
Признаки из `taxonomy.py` и графа — входы классификатора. CPA-метки — отдельный слой, проверяется, добавляет ли он информации сверх детерминированных признаков.
 
## Источники
 
- Graphectory: Liu et al., *Process-Centric Analysis of Agentic Software Systems*, arXiv:2512.02393 (OOPSLA 2026).
- CPA: Li, Li, Cheng, *Canonical Procedural Actions: An Auditable Annotation Protocol for Tool-Use Agent Traces*, arXiv:2609.24264.
- Act-ONOMY: SophiaGao/Act-ONOMY.
- CoALA: Sumers et al., 2023.
## Что известно о данных и коде
 
- Одна задача идёт во всех пяти средах, поэтому цепочки одной задачи зависимы. Для оценки классификатора делить выборку нужно по `dataset_task_id`, иначе точность завышена.
- Часть попыток пустая (без вызовов инструментов). Пустота сама по себе признак, но у `direct_mcp` она часто связана с `invalid_telemetry` (проблема импорта), а у `opencode` с `model_failure`. Эти случаи нужно различать.
- Поле `stream_kind` в `v_agent_trace_actions` и `v_agent_trace_full` может дублировать события между потоками (native, tool_trace, bridge). Без фильтра по `native` счётчики завышаются. Используется во всех скриптах, пока не отфильтровано.
- Фильтр `valid_for_scoring IS TRUE` пока не применён.
- В аргументах вызовов ключи различаются у разных моделей (например, `command` или `cmd`). Перед правилами по аргументам нужна проверка.
- Мысли ассистента могут быть на русском. Ключевые слова в графе и в `taxonomy.py` английские, для русских ответов классификация почти всегда даёт `other`.
- `n_cycles` в графе всегда 0: рёбра направлены только вперёд по времени.
## Порядок работы
 
1. Проверить `stream_kind` и `valid_for_scoring`, зафиксировать фильтры.
2. Проверить ключи аргументов по моделям и русский язык мыслей.
3. Запустить граф (`graphectory_pipeline.py`) и таксономию (`taxonomy.py`) на отфильтрованных данных, получить признаки по попыткам.
4. Классификатор связки (или харнесса) с разбиением по задачам. Сравнить наборы признаков: сырые имена инструментов, группы XEPV, таксономия, граф.
5. Отдельно: CPA-разметка на пилотной выборке и проверка, даёт ли она прирост к п. 4.
## Открытые вопросы
 
- Классифицировать связку «модель × харнесс» или отдельно харнесс и модель? При малом числе попыток на связку честнее второе.
- Что считать успехом классификации: точность, устойчивость между задачами или интерпретируемость различий?
- Нужна ли человеческая оценка CPA-меток, и на скольких эпизодах?
